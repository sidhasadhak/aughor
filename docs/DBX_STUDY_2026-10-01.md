# What dbx teaches about the database edge (study, 2026-10-01)

> **Why now.** The user, on `t8y2/dbx`, an open-source database manager with "100+ databases": *"I think there is
> a lot we can learn from it. Let's scan it, Deep, and check what's there for us?"* — then, on a screenshot of its
> data grid: *"Do we have a better SQL editor? Especially the result table part or DBX does?"* — then *"lets write
> a proper dbx roadmap first"*. This document is the measurement, then the proposal (Arc DE, ROADMAP §3.51).
> dbx was read at `e56754f` (2026-10-01); a path marked `dbx:` is relative to `github.com/t8y2/dbx` at that commit.
> Aughor was read on `main` at `f02c8f22`. Four readers took one area each — how dbx reaches its engines, its AI
> assistant and safety checks, dbx as a tool for other agents, and its SQL understanding and data tools — and a
> fifth pass compared the two result grids. Every claim about Aughor that a wave rests on was re-checked by hand;
> §7 says which were and which were not.
> **Adopted 2026-10-02** (ROADMAP §6 item 37), every clause as recommended, after the user removed DE-6 and moved its
> first part into DE-1.

## 1 · What dbx is, measured

- **A tool for people who administer databases**: browse and edit rows, migrate, diff schemas, run consoles for
  Redis, Kafka, MQTT and the like. A Rust core (`dbx:crates/`, 27 crates), a Vue desktop app on Tauri, a web
  server, a CLI, an MCP server, a plugin SDK, and a sidecar of Java and Go drivers (`dbx:agents/`).
- **"100+ databases" is three layers.** 108 product names in the picker
  (`dbx:plugins/connection-types/profiles/catalog.yaml`) map onto 85 connection-type files
  (`dbx:plugins/connection-types/*.yaml`); twelve MySQL-compatible products share `dbType: mysql`. Of the 85, 33 run
  native Rust drivers and 47 run through one sidecar protocol — JSON-RPC over stdin/stdout
  (`dbx:crates/dbx-driver-agent/assets/agent-protocol-v2.json`) — served by 53 sidecar drivers (36 Java, 15 Go,
  2 Rust). A JDBC engine on the shared base class is about twenty lines
  (`dbx:agents/drivers/exasol/src/main/java/com/dbx/agent/exasol/ExasolAgent.java`, 22).
- **Its job is not ours.** Most of its bulk is the write side: inline editing, DDL generated across engines,
  schema-diff deploy with rollback, data transfer. Aughor answers, governs and proves, and is read-only by design.
  This study takes only what serves the read side, and §5 says what it refuses.
- **Licence.** The root `LICENSE` is Apache-2.0; `dbx:agents/README.md:155` says AGPL-3.0. Until its authors
  resolve that, Arc DE takes ideas, never code.

## 3 · Where dbx is ahead

### 3.1 · One classifier, and the reads that can write

`dbx:crates/dbx-sql-core/src/sql_risk.rs` (1,961 lines) parses with sqlparser in the connection's dialect and sorts
every statement into read-only, write, DDL or transaction; anything it cannot classify counts as a write. It catches
the reads that can write — writable CTEs, `SELECT … INTO`, side-effect functions (`:601-617`, advisory locks and
their kin) — and, below the syntax tree, the shapes a parser drops: locking clauses (`:889-918`), MySQL executable
comments and `INTO OUTFILE` (`:745-760`, `:849-870`). Its tests (`:1662-1824`) are a ready list of cases.

Aughor's own layers are good: a first-token check, a syntax-tree mutation gate (`sql/readonly.py`), scored
patterns, the parse step, and a read-only engine session on DuckDB and Postgres. They are not applied evenly, and
that, not their quality, is finding 1.

### 3.2 · An outside agent has a policy

dbx's MCP server has one central policy (`dbx:crates/dbx-core/src/persistence/storage.rs:495`): read only, data
read/write, or full, with allowlists for connections, groups and tools, resolved global → group → connection →
database and reloaded on every call (`dbx:crates/dbx-core/src/ai/mcp_policy.rs`, 360 lines). A disallowed tool is
hidden from `tools/list` and refused when called; errors carry stable codes; every call writes a history row marked
as MCP; the environment can only narrow the policy. Its weak spot — with no saved policy the default is read/write
— is not one to copy.

Aughor's MCP server has one shared key, off by default, and `explore`, `deep_analysis` and `cancel_job` are always
exposed. Aughor is already stricter as a *consumer* of other MCP servers (each mutating tool needs a grant,
`mcpservers/models.py`). The gap is on the side that serves.

### 3.3 · An engine is a declaration

A dbx connection type is a YAML file: identity, a separate `dialect:` binding, runtime, default port, support level
and 16 capability flags (`dbx:plugins/connection-types/exasol.yaml:3-36`). A build step generates the Rust enum from
those files and asserts uniqueness (`dbx:crates/dbx-types/build.rs:32-96`); a script generates the TypeScript types.

In Aughor, Exasol appears in 14 non-test files: its connector, `connectors/base.py`, `connectors/registry.py`,
`connectors/catalog.json`, `tools/schema_linker.py`, `db/dialects.py`, `db/capabilities.py`, `db/schema_render.py`,
`sql/params.py`, `sql/writer.py`, `sql/join_guard.py`, and three hand-kept web maps (`web/components/AddDataPanel.tsx`,
`web/components/BrandLogos.tsx`, `web/lib/query/dialect.ts`). `catalog.json` is generated from the Python, the
reverse direction, and nothing keeps the web maps in step. Finding 5 is what a wrong declaration looks like when
identity and dialect are one field.

### 3.4 · Metadata says what it knows, and errors say what they are

`dbx:agents/metadata-constraint-coverage.tsv` lists 33 drivers, each with its metadata strategy (the engine's own
catalog, a shared fallback, or a deliberate fallback) and a reason, and a test holds every driver to its row. The
sidecar's errors carry a category, the session's state, and whether the operation may have reached the database; the
recovery policy retries only read-only metadata calls and never replays a person's SQL
(`dbx:crates/dbx-driver-agent/src/agent_recovery.rs:34-67`). Aughor reads no declared keys (finding 8) and knows a
dead connection only on Postgres and SQLite (finding 7).

### 3.5 · The result grid

dbx's grid is about 52,000 lines (`dbx:apps/desktop/src/components/grid`, `composables/useDataGrid*` and
`lib/dataGrid`; `DataGrid.vue` alone is 15,698). Aughor's is about 1,300 (`web/components/query/ResultsGrid.tsx`
635, `ResultsPanel.tsx` 522, `ResultFilterBar.tsx` 130). Most of the difference is the editing half, which Aughor
refuses. On the reading half:

| | dbx | Aughor |
|---|---|---|
| Rendering | virtual rows, plus a canvas mode | TanStack Table 9 and Virtual; only visible rows are drawn |
| Filter and sort | WHERE / ORDER BY bars and header filters rewrite the query and run it again (`dbx:apps/desktop/src/lib/dataGrid/dataGridColumnFilter.ts`), with distinct-value pick lists | filter chips over the returned rows only (`ResultFilterBar.tsx`), by design; sort in memory |
| Rows | pages and infinite scroll through the whole result, with an exact total and timing | stops at the row limit (500 by default, up to 50,000, `modes/SqlMode.tsx:66`) and says it was cut, proven by fetching one extra row |
| Column header | name and declared type | name only; the type sets alignment and is not shown |
| Row numbers, right-click menu | yes | no |
| Cell viewers | JSON tree, image, hex for binary, a map for geometry, a diff of two values | one text viewer that pretty-prints JSON |
| Foreign keys | click a key value to open the row it points to (`lib/dataGrid/dataGridForeignKeyNavigation.ts`) | none |
| Column layout | remembered per table | reset for each result, on purpose |
| Both | selection sum and average, transpose, find, copy | |
| Aughor only | | NULL as `∅`, distinct from `''`; Results N of M across a multi-statement run; one chart tab per visualization; pin, schedule, share; a signed provenance record per run; ⌘F find that moves without filtering, ⌘G go-to-row |

The editors are level: both are CodeMirror 6 with schema-aware completion. Aughor adds context actions (expand `*`,
add an alias, rename — `web/components/query/editor/intentions.ts`), a parameters bar, versions, a quick-fix panel
and the AI pane; dbx adds nine themes and running a `.sql` file.

### 3.6 · Column lineage: the idea, not the code

dbx's field lineage is regular expressions over view definitions and recent history
(`dbx:apps/desktop/src/lib/diagram/fieldLineage.ts:50-166`); a reader who ran it under Node got two false positives
on a two-query sample. Its ER auto-match has a confidence line that does nothing (`? "high" : "high"`,
`match-engine.ts:48`) and matched `orders.user_id` to `user_sessions`. Aughor's join inference is far stronger:
name roots with star-schema routing, value checks, measured cardinality, query-log mining, and a test that pins the
`order_items` case dbx gets wrong (`tests/unit/test_join_inference_dimension_owner.py:93`).

What is worth having is what dbx gestures at: which columns an answer depends on. sqlglot's `qualify` and
`lineage`, already a dependency, do it properly. A reader ran them over `evals/golden_sql_expanded.jsonl` against
`data/samples.duckdb` and resolved 130 of 136 output columns across 66 queries — the other six are `COUNT(*)` — at
about 4.7 ms a query. Aughor's lineage today is table-level: receipts record `("input","table:t")`, caveats filter by
table though rules are per column (`quality/caveats.py:88-106`, `quality/rules.py:67`), and `dependents_of` scans text
(`govern/lineage.py:74-78`).

### 3.7 · Smaller things

- CSV export neutralises formula triggers (`= + - @`, tab, carriage return) with a reversible `'` prefix
  (`dbx:crates/dbx-formats/src/csv_export.rs:44-77`). Finding 9.
- Import keeps numbers with leading zeros as text, and never turns an integer too large for int64 into a float
  (`table_import.rs:5156, 5188`, as a reader reported). Finding 10.
- Schema-diff rename detection scores table pairs at 0.6 × column-name overlap + 0.4 × type similarity and matches
  them one to one (`dbx:crates/dbx-core/src/schema_diff.rs:1020-1078`). Aughor rebuilds the graph when the table set
  changes (`ontology/graph_freshness.py:87-88`) and re-seeds the glossary below 0.6 column overlap
  (`semantic/autoseed.py:149-156`); a rename proposed into the candidate inbox (`ontology/candidates.py`) would keep
  metrics, rules and declarations.
- The CLI's skill installer writes `~/.agents/skills/dbx` with a SHA-256 manifest and refuses to overwrite local
  edits without `--force` (`dbx:crates/dbx-cli/src/agent_skill.rs`, 524 lines); every CLI command takes `--json`
  and reports errors as `{"error":{code,message}}`. Aughor's `SKILL.md` has no installer and its CLI no JSON output.
- The MCP server ships as a native binary behind a small npm launcher, one optional package per platform. Aughor's
  MCP server needs the whole checkout; a slim package that only speaks HTTP to the API would not.

## 4 · Where Aughor is ahead, and stays as it is

- **Schema context for the model**: row counts, sample values, value lists for low-variety columns, "no date column"
  warnings and annotations, trimmed to the tables involved and sized to the model's window (`db/schema_render.py`,
  `agent/schema_focus.py`, `llm/context_budget.py`). dbx caps by count: 50 tables, 40 columns.
- **Join inference** (§3.6).
- **Audit and PII**: every statement audited by what it is (GM-5), PII redacted after execution. A reader found no
  result redaction and no statement audit log in dbx.
- **Provenance**: the doors on every result (GM-3), a signed record per run.
- **Value search**: a trigram value index (`sql/value_index.py`), where dbx ORs `LIKE '%term%'` across every text
  column.
- **The results pane beyond the grid** (§3.5).

## 5 · What not to take, and why

1. **The write side**: inline editing, DDL generation and its 32 capability flags, schema-diff deploy, data
   transfer, and DML clean-up rules (one sets overflowing values to NULL). Aughor writes nothing to a warehouse.
2. **Hand-written dialect files**: 37 YAMLs, 4,877 lines, whose metadata queries only a test reads. sqlglot is the
   dialect layer.
3. **The lineage and ER-match code** (§3.6): measured false positives.
4. **Data compare**: both tables held in memory, and a "confidence" that is 0.95 × the sample rate.
5. **Raw-SQL MCP tools, and a read/write default.** Aughor's MCP tools ask questions; they do not take SQL.
6. **A localhost bridge with no token** for opening a table in the app; dbx's guard is a content type and a loopback
   Host header. Return a link instead.
7. **Importing DBeaver or Navicat passwords** with those vendors' fixed keys
   (`dbx:apps/desktop/src/lib/imports/dbeaverImport.ts:123-137`). If import is ever wanted, take host, port and
   database, and have the person enter the secret.
8. **A JDBC sidecar, now.** The long tail of engines it buys is real, but it needs a JVM beside the server, a driver
   store and a new trust boundary. Recorded for self-hosted installs, not scheduled (DE-7).
9. **The canvas renderer**, unless a measurement shows the virtual grid is too slow.
10. **The name.** Code built from this arc names each feature for what it does. The vocabulary ratchet already
    refuses other products' names in code (`tests/unit/test_vocabulary_ratchet.py:394-423`).

## 6 · The proposal: Arc DE, the database edge

Five waves, and DE-7 recorded for later. DE-6 was removed by the user on 2026-10-02 and its first part moved into DE-1;
the numbers were kept, so DE-6 stays empty. Each wave begins by re-measuring its premise. Only the first has a safety
consequence.

**DE-1 · The read-only promise holds at every door** (findings 1, 2, 6 and 11; closes the gate-map study's finding 5).
- The parse step runs at every connection's door, in that connection's dialect. It runs at the shared step
  (`security_pre` or `through_door`), not in each connector, so the next connector cannot forget it. `internal=` and
  the workbench's metadata rule keep their meaning.
- `SafetyChecker` parses in the connection's dialect. Today its syntax-tree checks, `is_mutating(sql)` and
  `disallowed_functions(sql)`, are called with none (`security/safety.py:113, 119`).
- `sql/readonly.py` learns what dbx's classifier knows: executable comments, locking clauses, and the side-effect
  functions (advisory locks, `GET_LOCK`, `set_config` of a read-only setting).
- The engine backs it where it can. MySQL opens its session read-only (`SET SESSION TRANSACTION READ ONLY`); Postgres
  keeps `default_transaction_read_only` and refuses the statement that would turn it off. Where an engine has no
  session-level read-only (BigQuery, Snowflake), `engine_read_only` says so and the doors on the result carry it.
- The door census asserts that every connector validates (`tests/unit/test_sql_door_census.py`).
- A refusal reaches the person as a refusal: the ALTER COLUMN endpoint reads the door's answer instead of
  reporting `applied: true` (finding 6, §3.49's leftover).
- Data stays data: schema samples and value lists reach the model fenced as untrusted data, with a length cap per
  value, as query rows already are (`db/schema_render.py:166-176`; `fence_untrusted` and `cap_cell` in
  `util/prompt_safety.py`). Finding 11; moved here from DE-6 at the user's word on 2026-10-02.
- **Pre-check, the risk:** run the parse step over the newest 2,000 statements in theLook's audit and over
  `evals/golden_sql_expanded.jsonl`, and count the valid statements sqlglot would refuse. If it refuses real
  BigQuery SQL, a parse failure in that dialect becomes a stated caveat rather than a refusal, and the token-level
  checks carry the weight there.
- **Receipt:** the nine statements of §2 before and after, through the real doors; one live MySQL run with the
  executable comment refused; the refusal count from the pre-check; a sample value worded as an instruction,
  reaching the prompt inside the fence. Mutation-tested.
- Small. No flag (§6 item 37(b)).
- **Built 2026-10-03** on `claude/focused-hamilton-8w0q1f`, not merged — ROADMAP §3.51's status paragraph holds the
  whole account. In short: the parse step moved into `_security_pre`, the one step every connector's door calls,
  reading the dialect `through_door` now records; `sql/readonly.py` learned the table above (lock clauses via
  sqlglot's `locks`, the side-effect functions, a command inside a block, and — from the text — the executable
  comment and `INTO OUTFILE`); MySQL connects read-only; the doors say `engine-read-write` where the engine has no
  session-level read-only; the ALTER COLUMN route reads the refusal; samples, value lists and the catalog's sample
  rows are capped and fenced. The nine statements of §2 are refused at every one of 14 connection classes before a
  driver is reached (`tests/unit/test_de1_read_only_at_every_door.py`), 12 mutations were each killed, and the
  pre-check read 0 of 53 golden statements refused in five dialects. Owed, because neither was reachable from the
  build machine: theLook's audit count (`scripts/de1_parse_step_precheck.py --connection 8233e4fd`) and the live
  MySQL refusal.

**DE-2 · An outside agent is a principal with a policy** (findings 3 and 4).
- **DE-2a, small:** the MCP client presents a principal, so identity mode works; the key is compared in constant
  time; `--http` requires a bearer token and rebuilds its transport security after the host is set. Pre-check: run
  `--http --host 0.0.0.0` and record what a remote client gets.
- **DE-2b, medium:** one agent policy per organisation. `read` looks things up; `run` also starts explorations and
  analyses, which spend model calls, and cancels them; `act` also takes the tools that change something (automation
  effects, Spotlight's acts). Allowlists for connections and tools. Kept with the organisation's settings, reloaded
  on each call, enforced in the API on requests the MCP client marks as its own. A disallowed tool is hidden from
  `tools/list` and refused by name; errors carry stable codes; the environment can only narrow the policy; every
  call is audited with its principal and bounded arguments; Aughor's own tools carry `readOnlyHint` and
  `destructiveHint`.
- **DE-2c, small:** the knowledge tools go through the API like the rest, so they read the same data with the same
  clearances.
- VA-10 (§3.5) owns identity and administration. DE-2 adds the outside agent as a kind of principal and builds no
  second identity system. §6 item 3's posture for the servers Aughor consumes is unchanged.
- **Receipt:** an MCP client with identity required, refused before and served after; a `read` policy that hides
  `explore` and refuses it by name; the audit page showing the call with its principal.
- **DE-2a built 2026-10-03** on `claude/focused-hamilton-8w0q1f`, not merged — ROADMAP §3.51's status paragraph
  holds the account. The pre-check ran live first: `--http --host 0.0.0.0` answered a remote client 421 on every
  request (the allowlist fixed at import, as inferred above) and a loopback client got a session for no credential.
  After: the client presents the principal it is given, the key is compared in constant time, `--http` needs a
  token every HTTP client presents, and the transport security follows the host. The first clause of the receipt
  above is in `tests/unit/test_de2a_mcp_principal.py`; the `read` policy and the audit page are DE-2b's.

**DE-3 · An engine is one declaration** (findings 5, 7 and 8).
- **DE-3a, small:** Exasol declares `exasol`. The receipt is the writer rules and the capability check reading
  Exasol's own (QUALIFY allowed), and a transpile test.
- **DE-3b, medium:** each engine is declared once — identity; fields and which are secret; the install extra; the
  sqlglot dialect; whether it runs SQL as written; parameter style; writer rules; constructs it refuses; support
  tier; metadata strategy — and the registry, `catalog.json` and the three web maps are generated from it, with a
  test that fails when a copy drifts. Adding an engine becomes one declaration and its connector.
- **DE-3c, medium:** metadata reads are typed — columns, primary keys, foreign keys, comments — each answered
  *supported*, *unsupported* or *unknown*, with a coverage table and a test that holds every engine to a row.
  Declared foreign keys join the join inference as its strongest signal, still checked against values.
- **DE-3d, small:** connection errors are typed (connection, timeout, cancelled, SQL). A connection error evicts the
  pooled connection; only statements the platform declared `internal=True` are retried, never a person's or a
  model's; every warehouse connector answers `is_healthy`.
- **Receipt:** one new engine added as a single declaration (§6 item 37(d)), seen in the add-data picker, the writer
  rules and the catalog; a Postgres schema with declared keys whose join inference shows them; a pooled connection
  killed mid-session and the next statement served without a failure the person sees.
- **DE-3a and DE-3d built 2026-10-03** on `claude/focused-hamilton-8w0q1f`, not merged — ROADMAP §3.51's status
  paragraph holds the account. Exasol declares `exasol` (finding 5), and the writer rules, the capability contract,
  the parse step and the transpile read it so; under `postgres` it had been told to avoid QUALIFY. Engine errors are
  typed by the driver's exception name and message (finding 7's other half), a lost connection is closed by the
  pool and never handed out, only a platform statement is run once more on it, and every connection class answers
  `is_healthy` where only Postgres and SQLite did. The receipt's third clause — a pooled connection killed
  mid-session, the next statement served — is proven on a fake connection whose first run fails; the live form
  waits for an engine one can kill, which DE-3b's Trino container is the planned stand-in for.

**DE-4 · Column lineage over the statements we run.**
- Every statement the agent and the workbench run is qualified with the schema and traced with sqlglot's lineage:
  which columns are outputs, filters, join keys and group keys. Each edge says how it was resolved — by the parser
  (certain), through an alias (likely), or by name only (possible). The edges ride the receipt that already records
  `("input","table:t")` (§6 item 37(f)); `govern/lineage.py` reads them instead of scanning text.
